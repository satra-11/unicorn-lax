# ADR 003: 選択画像のエクスポートオプション

## ステータス

承認済み (Accepted)

## 日付

2026-09-14

## コンテキスト

本アプリケーションは、ローカルに保存されている大量の画像からAIによって選別を補助するツールである。選別が完了した後、アルバム作成や印刷などの目的で、ユーザーが選んだ画像をPC内の任意のフォルダに書き出す・コピーできるようにする必要がある。

しかし、ブラウザ上で動作するWebアプリケーションであるため、セキュリティ上の理由からユーザーのローカルファイルシステムへの自由なアクセスは制限されている。さらに、保育園や幼稚園、学校などの様々な環境で利用されるため、多様なOSやブラウザ（Chrome, Edge, Safari, Firefox）をサポートするクロスブラウザ対応が必須である。

考慮すべき主な観点は以下の通り:

1. **機能性**: ユーザーが選定した写真群を、手元のPCの特定フォルダにまとめて保存できること。
2. **クロスブラウザ対応**: 非Chromium系ブラウザ（SafariやFirefoxなど）を利用するユーザーを完全に排除しないこと。
3. **ユーザー体験 (UX)**: ネイティブアプリケーションの「指定フォルダに保存」に近い、直感的でシームレスな操作感を提供すること。

## 決定事項

**ハイブリッドなエクスポート戦略** を採用する。

1. **メイン手法 (プログレッシブ・エンハンスメント)**: **File System Access API** (`showDirectoryPicker`, `FileSystemWritableFileStream`) をサポートする環境（主にChrome、Edge等のChromium系ブラウザ）では、このAPIを利用して指定フォルダに直接書き込む。
2. **フォールバック手法**: File System Access APIをサポートしていないブラウザ（Safari、Firefoxなど）では、**ZIPアーカイブ生成**（`jszip` 等のライブラリを利用）を行い、ZIPファイルとして一括ダウンロードさせる。

### 処理フロー (Workflow)

- ユーザーが「エクスポート」をクリックした際、アプリケーションは `window.showDirectoryPicker` の利用可否を判定する。
- **利用可能な場合 (Chromium系)**:
  - ユーザーに保存先フォルダを選択するダイアログを表示する。
  - アプリは選択された `File` オブジェクトを読み込み、指定フォルダ内に直接ファイルとして書き込む。
- **利用不可の場合 (Safari / Firefox等)**:
  - アプリは選択された `File` オブジェクトをブラウザメモリ上で1つの `.zip` アーカイブにまとめ、通常のファイルダウンロードとして提供する。

## 採用理由

1. **大多数のユーザーに対する最適なUX**: File System Access APIを利用することで、ユーザーが手動でZIPファイルを解凍する手間を省き、最も直感的な保存体験を提供できる。また、メモリ上で巨大なZIPファイルを構築する必要がないため、ブラウザのメモリ制限を回避できる。
2. **ユニバーサルなアクセシビリティ**: File System Access APIのみに限定すると、SafariやFirefoxユーザーが完全に利用できなくなってしまう。ZIP形式のフォールバックを用意することで、解凍の手間は生じるものの、すべてのユーザーが確実にエクスポートを実行できる。
3. **将来性への適応**: Web標準の進化に伴い、将来的に他のブラウザでもFile System Access APIがサポートされる可能性がある。プログレッシブ・エンハンスメントの設計により、ブラウザが対応した時点で自動的により良いUXへ移行できる。

## 検討した代替案

### 1. File System Access API のみを採用

- **メリット**: 優れたUX、低メモリ消費。
- **デメリット**: SafariおよびFirefoxユーザーで機能が完全に停止する。
- **判定**: 「多様な環境のユーザーをサポートする」という要件を満たせないため不採用。

### 2. ZIPアーカイブダウンロードのみを採用

- **メリット**: 100%のクロスブラウザ互換性。単一のコードパスで実装が容易。
- **デメリット**:
  - ユーザーが毎回ZIPファイルを解凍する必要があり、UXが劣る。
  - 高解像度の写真を大量（数百〜数千枚）にエクスポートする場合、RAM上に数ギガバイトのZIPを生成することになり、ブラウザがクラッシュするリスクが高い。
- **判定**: Chromiumユーザーに対して大幅に優れた体験を提供できる機会を逃すため、単独ソリューションとしては不採用。

### 3. ローカルAPIサーバー (Node/Nitro fs) の利用

- **メリット**: Node.jsの `fs` モジュール等を用いて絶対パスで高速に直接ファイルコピーが可能。
- **デメリット**:
  - セキュリティ上、ブラウザはファイルの絶対パスを難読化・遮断する。
  - ユーザーにローカル開発環境（`bun run dev` 等）の立ち上げを強いるか、ローカルサーバーへのアップロードが必要になり、「完全なクライアントサイドWebアプリ」というポータビリティが損なわれる。
- **判定**: 一般ユーザー（保育士や保護者）向けツールとして配布・利用のハードルが高すぎるため不採用。

### 4. Electron / Tauri 等によるデスクトップアプリ化

- **メリット**: ネイティブのファイルシステムアクセス、最高のパフォーマンスとOS統合。
- **デメリット**: ビルド・配布・アップデート運用の複雑さが大幅に増大する。現在のWeb完結というスコープに対してオーバーキル。
- **判定**: 現段階では不採用。将来的に専用デスクトップアプリとして展開する場合には有力な候補。

## 影響・結果

- **二重の実装・保守**: File System Access API向けとZIP生成向けの2系統の処理ロジックおよびテストが必要になる。
- **ZIP生成時のメモリ制限**: フォールバック環境（Safari等）で大量の画像を選択した場合、メモリ枯渇の恐れがあるため、選択枚数に応じた注意喚起メッセージや分割ダウンロードなどの配慮が推奨される。
